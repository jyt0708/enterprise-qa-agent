# 最难问题、学习收获、下一步

## 最难问题

### 1. AgentState 的传递与决策循环

比较难的是决定模型节点和工具节点之间应该传递哪些状态，以及哪些内容需要累积、哪些需要更新。
当前实现中，`messages` 通过 reducer 追加模型消息和工具观察；调用次数、证据集合、执行记录和最终结果则由节点返回更新。工具执行完后，需要把结果作为 `ToolMessage` 交回模型，并正确关联本次工具调用，模型才能根据观察选择下一步。

### 2. Pydantic 校验与模型纠错

另一个难点是Pydantic部分，[schemas.py] 用 Pydantic 定义文档、工具参数和最终答案，检查必填字段、字段类型以及状态之间的约束。例如，`answered` 必须有引用且不能存在未解决的缺口；`needs_clarification` 必须提供追问。知识库加载时，`TypeAdapter(list[Document])` 会对整个文档列表及其嵌套片段进行校验。

但结构校验不能证明回答正确，所以还要额外检查正确性。最终答案校验失败时，错误会交回模型，让模型有机会修正。


## 学习收获

之前做过类似的问答 Agent，但当时主要关注能否检索到资料并生成答案，忽略了资料版本、冲突处理和输出结构化，经常得到不规范的回答。这次项目让我把注意力更多放在证据来源、失败反馈和结果可核查性上。

- **文档版本和适用范围是回答的一部分。** 引用不仅要有文档 ID，还需要片段和版本日期。即使某份制度更新，也不能在缺少适用或替代关系时认定它优先。
- **结构校验和证据校验需要配合。** Pydantic 能减少漏字段和状态不一致的问题；引用校验能拒绝未读取的来源、错误版本和不属于原文的引文。但引文存在于原文，并不必然意味着它支持答案中的所有表述，仍需人工核对语义。
- **不同失败需要分别记录。** 资料不足、读取工具失败、模型接口失败和预算耗尽含义不同。


## 下一步

1. **减少无效动作并评估稳定性。** 对照 `trace.actual_model` 记录，分析不同模型的工具调用表现。后续可固定一个模型进行重复对照，记录通过情况、无效轮次和调用次数，避免仅凭一次成功判断效果。
2. **加强检索改写和冲突验收。** 当前检查器能够检查关键词、引用文档、不同查询数量及是否读取冲突双方，但不能完整判断答案是否保留所有限定条件。
3. **在现有场景稳定后扩展故障评估。** 后续可以增加评估场景，比如 “每次读取失败” 和 “每次检索失败” 的场景。观察模型能否停止无效重试并如实返回失败或未完成状态。
4. **效率与稳定性** 当前T01~T08均通过自动检查，总共56次模型调用里有25次协议错误 protocol error [summary.json]， 占45%，执行效率和稳定性仍需改善。T04最明显 (../examples/live/full-run/T04.json)，由于程序每轮只接受一个动作，而模型多次请求读取多个片段，导致整批请求被拒绝返回协议错误，虽然结果正确但最后达到10次调用上限。 (关于为什么选择设计程序只接受一个动作，见 [02-solution.md])
